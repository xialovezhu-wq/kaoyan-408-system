# Native Luna Parallel Contract

This contract applies only to native Luna delegation explicitly requested by the user in the current task. An owning workflow's instructions or a historical approval do not independently authorize children. Preserve explicit authorization within the same task and its stated scope; otherwise the parent performs the work serially. Math, 408, and English retain their own evidence and transaction rules; this contract never creates a separate background Provider, MCP consumer, worker, queue, or report pipeline.

A historical Luna reference alone does not authorize reactivation. Current user,
root-task and subject instructions take precedence over an older compatibility
contract; keep a retired route retired unless the current task authorizes it.

## Eligibility

After explicit user authorization, delegate only a bounded subtask that can proceed independently alongside useful parent work and has an independently checkable result. Without that authorization, even an owning workflow's Luna requirement does not permit a child. Preserve any real execution-identity requirement truthfully and report a concrete unsupported serial step rather than fabricate a leaf run. Split by meaningful outcome or evidence scope, not arbitrary file counts.

## Runtime identity

Use a Luna role or model supported by the current runtime; generic role names do not prove a particular model. Preserve an explicit model/effort requirement from the owning workflow, but do not add a service-tier requirement or universal fork mode. Choose context isolation according to the evidence boundary and supported tool schema.

Each requested Luna worker is a leaf. Distinguish configured identity, verified execution metadata, and unavailable fields. Missing metadata does not authorize changing global configuration or the parent's tier. Do not claim a required runtime identity was verified when it was not; the parent must resolve any acceptance step that actually depends on that identity.

## Task envelope

Every child receives all of the following:

1. objective and independently checkable deliverable;
2. exact input and evidence boundary;
3. read-only scope or one exclusive write-path set;
4. required return schema;
5. acceptance command or evidence check;
6. stop condition;
7. an explicit prohibition on further delegation.

## Fan-out, waves, and barrier

Use the minimum children needed for the explicitly delegated scope, within the user's count and total limits and the runtime's capacity. Runtime capacity is not a target. Track each assigned workflow to a terminal result.

Wait for the results needed to complete the current task. The parent rejects wrong-scope, wrong-hash, unauthorized mutation, and incomplete evidence; resolves conflicts; and performs final validation. Treat unverified runtime metadata according to the owning workflow's actual requirement. Do not add peer voting or repeated critique rounds; preserve any separately approved artifact QA requirement.

## Single-writer boundary

The parent owns architecture, approval, shared state, locks, receipts, IDs, formal transactions, conflicting paths, cross-shard deduplication, final assembly, and final acceptance. Parallel writes are allowed only when workers own mutually exclusive files and no shared index or transaction is touched. The same file, ledger, receipt, formal repository transaction, or ID namespace always has one writer.
